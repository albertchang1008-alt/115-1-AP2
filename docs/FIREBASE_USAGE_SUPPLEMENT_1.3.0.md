對象：Codex
主規格：`docs/STUDENT_UI_REDESIGN_1.3.0.md`（第三版）
狀態：1.3.0 已完成本機實作（commit `af760e4`），**尚未部署**。本補充規格的項目要在部署前一併完成。
日期：2026-09-18

---

## 0. 為什麼現在做

規模預估：**約 200 位學生。日常每人一天 20 次以上作答，考前每人 50 至 100 次。**次單元切小後，學生會在同幾個次單元反覆練習。

| 情境 | 條件 | 一天作答次數 |
|---|---|---|
| 日常 | 200 人 × 20 次 | 4,000 |
| 考前 | 200 人 × 50 次 | 10,000 |
| 最壞 | 200 人 × 100 次 | 20,000 |

目前每次「開始作答」都完整重讀題庫、每次「交卷」重讀所有 chunk 批改。最壞情況會遠超 Firestore 免費額度（每日 5 萬次讀取），因此第 1、2 節不是選配，**必須在部署前完成**。上線後再改要處理已存在的快取與資料。

**第二版變更**：估算基準改為上表；納入 1.3.0 第四版新增的綜合練習與錯題結構（第 2.5 節）；作答次數的統計對象包含完整測驗、閃卡、抽題、錯題複習與綜合練習。

**目標**
1. 同一題庫版本在同一裝置上不重複讀取（第 1 節）。
2. 交卷批改的讀取量與題數脫鉤（第 2 節）。
3. 完成一次全系統用量盤點，確認沒有其他熱點（第 3 節）。

**不可退讓的前提**
- 分數仍由後端依正解批改，不得回到前端計分。
- 題庫版本雜湊、`best`、`wrong`、`attempted`、完成度規則版本、逐班開放與 `visibility` 過濾全部不變。
- 學生端畫面與操作流程不變（本補充不改 UI）。

## 1. 前端題庫快取（優先度最高）

### 1.1 目標
同一個 `courseId + unitId + version` 的題庫，在同一裝置上只從後端讀取一次；之後開始測驗、閃卡、抽題、錯題複習都直接使用本機資料。

### 1.2 版本判斷
- 快取有效的唯一條件是**題庫版本字串完全相同**。版本是內容雜湊，內容有改就會換版本，所以不需要額外的過期機制。
- **優先確認 `bootstrap` 回應是否已包含各次單元目前的題庫版本。**
  - 有：命中快取時可以完全不呼叫 `getBank`（讀取 0 次）。
  - 沒有：在 `bootstrap` 回應中加入每個可見次單元的題庫版本（此資料來自課程 `published`，不需要額外讀取）；若不可行，改為呼叫既有入口取得版本後再比對，並在回報中說明讀取次數。

### 1.3 儲存
- 使用 `localStorage`（與色系、字級一致），鍵名例如 `bank:<courseId>:<unitId>:<version>`。
- 寫入前先 `JSON.stringify` 並檢查大小；單一題庫超過 1 MB 就不快取（直接使用，不寫入）。
- 總量上限約 3 MB，超過時以最久未使用（LRU）淘汰；記錄每個快取的最後使用時間。
- 同一次單元只保留最新版本，寫入新版本時刪除該次單元的舊版本鍵。
- **所有讀寫都要 try/catch**：`QuotaExceededError`、無痕模式、內容毀損、JSON 解析失敗時，一律靜默退回呼叫後端，不得讓學生看到錯誤。
- 讀回的資料要做基本結構驗證（陣列、必要欄位齊全、題數與 manifest 一致），不通過就丟棄並重新取得。
- 學生登出或切換帳號時清除所有 `bank:` 開頭的鍵。

### 1.4 注意事項
- 快取內容包含正解。這與現況一致（題庫本來就連正解送到前端），但資料會留在裝置上，所以登出清除是必要的。
- 快取只在學生端使用；教師預覽與報表不使用快取。
- 抽題、錯題閃卡、完整閃卡、完整測驗與綜合練習共用同一份快取。錯題閃卡只從快取取題，不產生寫入。綜合練習會一次使用多個次單元的題庫，命中快取時不應產生額外讀取。

## 2. 伺服器專用答案表（交卷批改）

### 2.1 目標
交卷批改不再讀取全部 chunk，讀取次數與題數脫鉤。

### 2.2 資料
- `publishBank` 發布題庫時，額外寫入一份只含批改所需資料的文件，例如 `banks/{courseId}_{unitId}_{version}/grading`（實際路徑依既有結構調整）。
- 內容：`{ [questionId]: answer }`，以及題數等批改需要的最小欄位。165 題約數 KB，遠低於單文件 1 MB 上限。
- **此文件絕對不可出現在任何學生端回應中**，`getBank` 與其他入口都不得回傳。Firestore rules 維持 deny-by-default，客戶端本來就讀不到，但仍請覆核。
- 答案表由題庫內容產生，不改變版本雜湊的計算方式。

### 2.3 批改流程
- `submitAttempt` 依 `courseId`、`unitId`、版本讀取答案表（1 次讀取）批改。
- **舊題庫沒有答案表**：找不到時退回既有的讀 chunk 批改流程，並在後端記錄一次警告。不需要遷移腳本；教師重新發布該次單元後就會產生答案表。
- 完整作答的題數驗證、`best`、`wrong`、`attempted` 更新規則一律不變。
- 前端送來的 `correct`、`score` 一律忽略（維持現況）。

### 2.5 綜合練習與錯題結構的影響（主規格第四版新增）
- **綜合練習**（主規格 5.6）：一次涵蓋 `current` 的多個次單元。
  - 開始練習：範圍內每個次單元的題庫各一份（有快取時多半為 0 次讀取）。
  - 交卷：題目來自多個次單元，錯題與 `attempted` 要寫回各自次單元。請比較「沿用既有入口分次寫入」與「新增專用入口一次寫入」的讀寫次數，選擇較低者並在 `docs/FIREBASE_USAGE.md` 中列出兩者數字。
  - 批改需要多個次單元的答案表：請確認是否可在一次請求中批次讀取，並列出讀取次數公式。
  - 請給出建議上限（範圍內次單元數與總題數），超過時卡片提示並限制題數。
- **錯題結構**（主規格 5.7、7.8）：錯題改為記錄次數與最後答錯時間，錯題複習交卷後會更新錯題清單。
  - 錯題閃卡不作答、不寫入；錯題清單只在完整測驗、完整閃卡、抽題、綜合練習交卷時更新，請據此估算寫入量。
  - 時間範圍篩選與各範圍題數計算都在前端以已取得的進度資料進行，不得為此新增讀取或呼叫。


### 2.4 預期效果

| 情境 | 交卷讀取 |
|---|---|
| 現在（25 題／約 2 chunk） | 約 3 次 |
| 現在（165 題／約 9 chunk） | 約 10 次 |
| 改後（任何題數） | 約 2 次 |

## 3. 全系統 Firebase 用量盤點（本補充的主要交付項目）

### 3.1 要產出的表
請實際檢視程式碼，列出**每一個學生端與教師端操作**造成的 Firestore 讀寫次數，寫成 `docs/FIREBASE_USAGE.md`：

| 欄位 | 說明 |
|---|---|
| 操作 | 例如「學生登入取得課程」「開始完整測驗」「交卷」「讀取互動教材並回報事件」「開啟錯題複習」「教師開啟報表」 |
| 入口 | Callable 名稱 |
| 讀取次數 | 以公式表示，例如 `1 + chunk 數` |
| 寫入次數 | 同上 |
| 受什麼影響 | 題數、活動數、學生數、班級人數等 |
| 最佳化後 | 本補充完成後的數字 |

### 3.2 要一併檢查的項目
1. **`bootstrap`**：是否每次進入學生端都完整重讀課程？可否以版本或時間戳記避免重複讀取？
2. **`getProgress`、`getHistory`**：呼叫頻率、是否在畫面切換時重複呼叫。主規格要求切換分頁不得新增呼叫，請確認實際行為。
3. **`saveLearningEvents`**：互動教材事件是否有批次送出與節流。學生快速捲動圖卡時的最壞情況寫入次數是多少。
4. **`saveExplanationResearchEvents`**：同上。
5. **`saveActivity`**：YouTube 播放位置的寫入頻率，是否有節流。
6. **教師報表與結算**：`aggregate`、快照匯出的讀取量隨學生數與題數的成長方式；200 人時開啟一次報表要讀多少。
7. **索引成本**：`diagnostics` 文件的 `summary` 欄位尚未加入索引排除設定，與 `attempts.answers`、`reports.modes` 的既有作法不一致。請確認並在本補充一併加入排除設定（`firestore.indexes.json` 或欄位覆寫），同時說明對既有資料的影響。
8. **Cloud Functions 呼叫次數**：一天 4,000 次測驗會產生多少次函式呼叫，與免費額度的距離。
9. **儲存量**：題庫、事件、診斷資料一學期的預估成長。

### 3.3 估算基準
用以下基準各算一組日用量，放進 `docs/FIREBASE_USAGE.md`：

| 情境 | 條件 |
|---|---|
| 日常 | 200 人，每人 20 次作答、3 次教材閱讀 |
| 考前 | 200 人，每人 50 次作答、5 次教材閱讀 |
| 最壞 | 200 人，每人 100 次作答，其中一半集中在 2 小時內 |

作答次數包含完整測驗、完整閃卡、抽題與綜合練習（錯題閃卡不作答、不寫入，另計為讀取情境）。請假設其中約三成是綜合練習，並另外假設每人每天 5 次錯題閃卡，在報告中標明假設。

每組都要標出：最佳化前、最佳化後、與免費額度（每日 5 萬次讀取、2 萬次寫入）的比例。尖峰情境請額外標出每分鐘的最大讀寫，用來判斷是否可能觸發限流。

### 3.4 建議清單
盤點後列出還值得做的最佳化，每一項標明預期效果、風險與工作量，**但不要直接實作**，等教師決定。第 1、2 節的兩項則要在本輪完成。

## 4. 測試

1. 快取命中：同一版本第二次開始測驗不呼叫 `getBank`（或不讀 chunk，依 1.2 的實作結果）。
2. 版本變更：題庫改版後快取失效並重新取得；舊版本鍵被刪除。
3. 快取毀損或 JSON 無效：自動退回後端取得，不拋錯。
4. 寫入超出配額：捕捉例外，功能正常。
5. LRU 淘汰：超過總量上限時淘汰最久未使用者。
6. 登出清除 `bank:` 鍵。
7. 答案表批改：與讀 chunk 批改的結果完全一致（同一份題庫、同一組作答）。
8. 舊題庫無答案表時，退回 chunk 批改且結果正確。
9. 答案表不出現在 `getBank` 或任何學生端回應中。
10. 前端送假的 `correct`、`score` 仍不影響後端結果（既有測試維持）。
11. 綜合練習命中快取時不產生額外題庫讀取。
12. 錯題時間範圍篩選與題數計算不產生額外讀取。
13. 錯題閃卡不產生任何寫入，且不產生額外題庫讀取（共用快取）。
